# 成本优先的中枢派工

政策修订：2026-10-26。查看公开变更摘要与验证边界时，读取 [修订说明](references/revision-2026-10-26.md)。

## 目标与适用范围

优化任务达标的总成本：执行、上下文、返修、调度和核验一起考虑。中枢主要负责联网获取信息、与用户对接需求、提出项目规划意见，以及拆解、派工和验收；实际开发由能胜任的最便宜执行者完成。适用于代码、写作、设计、研究、报表和学习项目，不要求 Git 或完整长期计划包。

本 skill 明确要求：实际开发任务交给子代理或当前授权范围内的已有执行对话；只有用户明确要求创建独立对话时才创建侧栏任务。细小开发改动合并为一个有验收标准的任务包，或交给已有执行者，不以“顺手就能改完”为由让中枢接管开发。

只在当前任务范围内调度。保持主会话的模型设置；按本规则设置执行者的模型。用户当前明确指定的模型、推理强度、禁止委派、预算或项目边界优先。此规则不授权扩大任务、发布、删除资产或修改无关对话。

## 中枢与执行者的职责

**中枢直接承担：**

- 与用户讨论目标、使用场景、优先级、取舍和反馈；给出有依据的建议，区分已确认决策与待讨论方案。信息已充分时继续推进，不把所有常规细节都变成确认问题。
- 联网搜索官方文档、技术信息及候选方案，核对时效和来源，综合为项目决策；批量资料整理或有独立交付的深入调查可派给执行者。
- 少量只读查看项目结构、接口、关键文件和交付证据，以形成任务边界；大范围代码追踪、复现排错交给执行者。
- 制定或修订规划、任务卡、接口约定、依赖和验收标准，维护进度、决策及派工规则等管理文档。
- 选择模型、调度执行者、解决职责和依赖冲突，向用户汇报；检查差异、证据和实际结果，做必要的轻量抽查并决定接受、返修或升级。

**执行者承担：**功能实现、代码与运行配置修改、重构、调试修复、测试代码、构建和完整验证，以及计划要求的具体交付产物。涉及实际开发的集成和冲突修复也交给执行者；中枢组织集成并核验结果。

默认保持这一分工。用户明确要求中枢亲自实施或禁止委派时，遵循其指示；执行工具暂不可用时，先继续调研、沟通和规划等不受影响的工作并说明实施阻塞，不静默把全部开发转到中枢。子任务失败后升级的是执行者的模型，中枢负责交接和判断，不因多次失败自动亲自重写实现。

中枢可直接编辑管理文档和本类派工 skill；修改应用配置、开发脚本或产品文件属于实施，不能包装为管理工作。规划与验收不要求中枢重新实现一遍或重复运行完整测试；需要深入验证时派出适当的验证执行者。

## 1. 先判断任务是否可派发

派发前用一张短任务卡说明：目标与完成标准、输入/事实来源、允许修改的范围、必须保留的约束、依赖状态、验证方法、输出位置、执行者角色。资料不足时先做有边界的调查，不能把“尚未提供必要信息”算成便宜模型能力不足。

按未解决的判断难度选模型，而不是按项目名称、文件数、文字量、预计运行时长或“最终审查”这样的称谓选模型。已由中枢确定的设计不再重复计入执行难度。可以把复杂任务中的资料提取与既定方案实施拆给便宜模型，保留真正困难的决策给强模型。

执行者开始实施前，检查必需输入和规则入口可读、允许范围与验收无冲突；有缺项先回报中枢处理，不逐项向用户重复确认。

## 2. 选择最低合格档位

以下是作者环境的路由配置示例，不是模型在所有任务上的严格性能排名，也不保证这些 model ID 在其他环境可用。L、S、A、U 是政策档位；Luna、Sol、Astra 的顺序是本配置的成本假设，使用者须依据自身工具 schema、可用模型、实际计量与任务证据建立对应关系。只使用当前运行环境明确支持的模型和强度；不硬编码美元价格或承诺固定节省比例。适配方法见 [工具适配与交接](references/tool-adapters.md)。

| 档位 | 实际模型 / 推理强度 | 入选条件与典型工作 |
| --- | --- | --- |
| L | `gpt-6-luna` / `high` | 目标和规则明确、上下文可收敛、结果可核验、修改可隔离。检索提取、按模板整理、已有范例的小功能、已定位问题修复、按确定大纲局部改稿、既定检查。纯机械提取可用 `low`。 |
| S | `gpt-6.1-sol` / `medium` | 需要设计、多步工具工作或复杂实施，但目标稳定、约束可列举、验收可定义。完整模块、跨模块接入、有证据的研究综合、文本修订及有明确约束的架构规划；先用本档评估实际结果。 |
| A | `gpt-6-astra` / `medium` | S 已出现确证的能力失败，或有具体证据表明耦合约束、长期一致性及高判断负荷已超出 S 的可控范围。仅有“架构”“跨模块”“最终审查”等任务名称不构成首发 A 的理由。 |
| U | `gpt-6-astra` / `ultra` | A 经证据确认仍存在深层推理瓶颈，且进一步推理有明确用途；或任务一开始已有同类失败证据证明必须用该档。作为最后一次执行机会。 |

L 的首发门槛：上述目标、规则、上下文、验收、隔离五项均满足。否则说明缺的是哪项：可补足就补任务卡；需要设计或综合判断时优先 S；有具体能力差距证据才首发 A。特别困难且证据充分才 U。

模型适配或更新不自动修改主会话或全局模型设置，不重置旧任务已用的返修次数，也不改写历史执行记录。工具可用性与参数映射见 [工具适配与交接](references/tool-adapters.md)。

从 L 开始判断，不要求所有任务先实际跑一遍 L。跳级只需记录一个具体能力理由，无需为已授权范围内的选模逐次询问用户。质量要求保持不变，不能为省钱降低验收标准。失败代价高时先隔离修改、完善验证；这些措施仍不足以覆盖判断风险才提高首发档位。

推理强度不逐档爬梯：默认使用表中档位，不自动轮流尝试 low/medium/high/xhigh/max。只有新证据表明更深的同模型推理值得投入时，才能将一次同档定向修复机会用于调高强度，并记录理由；它仍消耗同一重试额度。

## 3. 真正设置模型并交付任务卡

首次使用一种派发工具、需要改变已有执行者模型或恢复中断任务时，读取 [工具适配与交接](references/tool-adapters.md)，核对当前 schema。通过真实模型/推理参数设置，不以提示词代替配置。

首发至少记录：任务标识、执行者 ID、输入/工作目录、选档理由、请求模型及强度、工具回显的有效配置（没有则写“已请求，未回显”）、尝试历史、验收条件。使用项目已有节点卡/状态表；没有时，多轮任务只维护一份简短路由记录，位置先核对项目写入约定。一次性短任务可以记录在对话中，不为它创建一套计划目录。

限制调度开销：默认最多同时运行 2 个执行者，并受平台/用户更低上限约束；并行工作应彼此独立。共享工作区时明确文件所有权，必要时使用独立 worktree 或候选输出目录。一个修改范围同一时刻只有一个写入者。

执行者收到 `role: worker`，只完成任务卡；遇到升级或额外派工需要时回报中枢，不自行递归扩张代理。中枢批量派发相关小工作，不为一行改动建立独立执行对话。

同一上下文、修改范围和验收目标的连续小改动优先合并交给已有执行者；独立验收与并行收益不足以抵消交接成本时，保持一个任务包。

验收时在既有记录中补记首发是否通过、派发至验收的实际时长、返修与中枢深入核验次数；未知值写“未记录”，不事后猜测。一次性短任务仍可仅记录在对话中。

长任务在任务卡中给出阶段检查点与停止条件，并沿用用户已有的时间或用量上限；没有用户预算时，中枢设定与交付规模匹配的进度检查点，无需额外询问。到点回报成果、剩余问题和下一步，由中枢按进展继续或收敛范围；检查点不是完成期限，也不自动构成能力失败。父任务汇总各子任务的投入，拆分节点不重置用户预算。首次记录多轮任务或评估路由效果时，读取 [效果记录与预算](references/measurement.md)。

## 4. 验收和失败分类

执行者返回 `PASS`、`CAPABILITY_FAILURE` 或 `BLOCKED`，连同实际改动、检查结果、证据位置、未解决项及失败原因。状态是候选结论，中枢对照任务卡核验；自称完成、无输出、工具调用成功都不等于任务完成。

尚未执行或检查未结束时记录 `PENDING` / `VERIFYING`，不能写成“PASS，待验证”。路由选择正确只代表可派发，不代表产物验收通过。

- `PASS`：产物存在且满足任务卡；检查覆盖关键变化；限制与未验证项如实说明。已有证据足够即接受。日常 L 工作不默认再让 A 重做或全面复审，采用对应的自动检查或针对性抽查；高判断风险再安排独立审查。
- `CAPABILITY_FAILURE`：输入充分、工具可用，仍误解明确约束、产出违反验收条件、无法解释关键矛盾或无法提出有证据的修复。记录具体差异/错误，进入升级规则。
- `BLOCKED`：权限、登录、配额、模型不可用、缺依赖、网络、工具故障、尚待用户决定或输入不全。优先在授权内处理阻塞或报告所需信息；换更强模型不能算作解决。

一次测试失败本身不是能力失败。先确认是实现问题、测试本身/环境问题还是既有失败。创作和研究任务使用明确的事实、设定、范围和风格标准验收，不用中枢个人偏好无限返稿。

归类能力失败前，核对失败涉及的约束是否已明确传入任务卡、所需输入是否可用；交接遗漏先修正任务卡并记录交接返工，不据此升级模型。若已正式实施，仅在非 U 且仍有可用额度时允许因交接遗漏重新派发，并消耗一次同档定向修复及总执行轮额度；已到 U 或额度已用尽时报告交接瓶颈，不为绕过上限升级模型。实施前的输入检查阻塞不算执行失败，但所有投入均受任务总预算约束。

## 5. 有上限的升级

一般路线：`L → S → A → U`，允许根据新暴露的难点跳过明显不合格档位。保持原验收标准、有效成果及失败证据，只把未解决的部分交给新档位。

交接列明已接受成果、证据位置及允许修改的未解决部分；已接受成果只在新证据表明存在依赖缺陷时重新打开，并记录理由。

- 每个任务最多经过 4 个档位各一次；整条路线合计最多再加 1 次同档定向修复，总计最多 5 次执行轮。执行轮指一次正式派发/返修的工作回合，不是其中每次工具调用；已实施后的交接返工同样计数。五轮上限不替代单轮检查点或任务总预算。
- 同档修复仅用于定位明确、可用新证据纠正的小失误或遗漏；更适合强模型的瓶颈立即升级，不强制便宜模型先失败两次。
- U 是终点，不再提供同档修复。U 未通过、5 轮用尽或继续需要改变目标/边界时，保存可用成果，说明瓶颈和下一项决策，停止自动重试这一节点；继续不受影响的工作。
- 超时或响应不确定时先查询原执行者和产物，确认是否仍在运行；不能重复启动同一写入任务。真正的环境故障不耗能力升级次数，但相同未变化的阻塞不重复提交。
- 恢复时读回尝试历史、实际工作状态和已用修复次数。更换执行者、换对话或压缩上下文不会重置预算。

## 6. 与长任务计划协作

若项目已经使用 Planner/Manager，模型政策在规划时写入节点卡，Manager 读取节点选档及升级历史执行。沿用项目已有依赖、审批与合入约束；本 skill 不另建同类台账。

旧计划明确锁定某模型时保留其约定，不能静默把已批准的 Astra 节点降为 Luna。用户明确要求按本新政策迁移旧计划时，可在既有授权范围内修订选模字段并记录来源；否则先说明冲突。常规新派工使用本政策，不要求额外引入 APPROVED 计划包、Grill 或 Git。

## 完成标准

每个接受的结果都能追溯到任务、产物与验收证据；每次升级都有失败依据和真实参数请求；未解决节点有明确状态和失败出口。向用户简要汇报结果、实际请求过的模型以及必要的升级原因。没有平台计量时只报告模型和轮次，不推算“实际花费”或宣称“已省多少钱”。
